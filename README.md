# Autonomous Balloon Interception Simulator

## Version 0.2 -> this new version improves the physics behind the rocket model and prepare the environment for a reinforcement learning approach

A small 2D autonomous vehicle simulator written in C++ using Qt 6.

The purpose of Version 0.1 is to establish the software architecture and basic simulation framework that will later support more advanced physics, computer vision, reinforcement learning, and embedded control.

Version 0.1 deliberately avoids machine learning and computer vision.

The rocket is controlled entirely by a deterministic interception algorithm that has direct access to the positions of the rocket and balloon.

---

# 1. Objective

The simulation contains:

* a 2D world
* a rocket
* a stationary balloon
* a physics simulation
* an autonomous controller
* collision detection
* a Qt graphical interface

After starting the simulation, the rocket autonomously attempts to reach the balloon.

The simulation ends when:

1. the rocket reaches the balloon → **SUCCESS**
2. the rocket leaves the simulation area → **FAILURE**
3. a maximum simulation time is reached → **FAILURE**

There is no human control.

---

# 2. Coordinate System

The simulation uses a Cartesian coordinate system.

The world is represented using:

* `x` → horizontal position
* `y` → vertical position
* `theta` → rocket heading angle

The mathematical convention is:

* `theta = 0` → rocket points in the positive X direction
* positive angles rotate counter-clockwise

The rocket's forward direction is:

```text
             forward
                ↑
                |
                |
               🚀
```

The thrust force acts along the rocket's heading.

For a thrust magnitude `T` and heading `theta`:

```text
Fx = T * cos(theta)
Fy = T * sin(theta)
```

---

# 3. Simulation Loop

Each simulation step follows this sequence:

```text
┌─────────────────────┐
│  Current simulation │
│       state         │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│     Controller      │
│                     │
│ state → action      │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│       Physics       │
│                     │
│ state + action      │
│        ↓            │
│    new state        │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Collision / bounds  │
│      checking       │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│    Qt rendering     │
└─────────────────────┘
```

The controller is deliberately separated from the simulator.

This will allow the deterministic controller to be replaced by a reinforcement-learning controller in a future version without modifying the physics engine.

### Responsibilities

* store position
* store velocity
* store heading
* store angular velocity
* store throttle

```cpp
QPointF m_position;
```

### Important parameters

### Main methods

```cpp
void setThrottle(double throttle);
void setRudder(double rudder);

QPointF position() const;

double angularVelocity() const;
```

The `Rocket` class must not depend on the Qt graphical interface.

It represents the simulated physical object.

# 6. `State`

Represents the information available to the controller.

```cpp
struct State
{
    QPointF rocketPosition;
    QPointF rocketVelocity;

    double rocketHeading;
    double rocketAngularVelocity;

    QPointF balloonPosition;
};
```

Version 0.1 gives the controller perfect knowledge of the balloon position.

This is intentional.

There is no simulated camera yet.

---

# 7. `Action`

Represents the commands generated by the controller.

```cpp
struct Action
{
    double throttle;
    double rudder;
};
```

Expected ranges:

```text
throttle ∈ [0, 1]

rudder ∈ [-1, 1]
```

where:

```text
-1 → maximum left turn
 0 → no turning
+1 → maximum right turn
```

---

# 8. `Controller`

An abstract interface defining how a controller interacts with the simulator.

```cpp
class Controller
{
public:
    virtual ~Controller() = default;

    virtual Action computeAction(const State& state) = 0;
};
```

The simulator will only depend on this interface.

---

# 9. `SimpleController`

The first controller used in Version 0.1.

Its purpose is to autonomously steer the rocket toward the balloon.

It receives the complete simulation state.

### Basic algorithm

1. Calculate the vector from the rocket to the balloon.

```text
targetVector =
    balloonPosition - rocketPosition
```

2. Calculate the desired heading:

```text
desiredHeading =
    atan2(targetVector.y(), targetVector.x())
```

3. Calculate the angular error:

```text
angularError =
    desiredHeading - rocketHeading
```

4. Normalize the angular error to:

```text
[-π, +π]
```

5. Use the sign and magnitude of the angular error to determine the rudder command.

Conceptually:

```text
rudder = Kp * angularError
```

with the result limited to:

```text
[-1, +1]
```

6. Apply an appropriate throttle command.

The initial controller may use a simple constant throttle or reduce throttle when the rocket is badly misaligned.

The controller is intentionally simple.

The goal is not to create the optimal controller, but to create a working baseline that can later be compared with an RL controller.

# 10. `Simulator`

The simulator owns the physical objects and advances the simulation.

### Responsibilities

* contain the rocket
* contain the balloon
* obtain the current state
* ask the controller for an action
* apply the action
* advance physics
* detect collisions
* detect simulation failure
* maintain simulation time

### Conceptual interface

```cpp
class Simulator
{
public:
    Simulator();

    void reset();
    void step(double dt);

    State state() const;

    bool isFinished() const;
    bool isSuccessful() const;
};
```

The simulator should not know whether the controller is a simple mathematical controller or a future RL controller.

---

# 11. `SimulationWidget`

Qt-specific graphical component.

Its responsibility is visualization only.

It should:

* draw the simulation world
* draw the rocket
* draw the balloon
* optionally display simulation information
* request repainting when necessary

It should not contain the physics equations.

The widget uses `QPainter` for rendering.

Conceptually:

```cpp
void paintEvent(QPaintEvent* event);
```

will draw:

```text
┌─────────────────────────────────────┐
│                                     │
│                         ○ Balloon    │
│                                     │
│                                     │
│             ▲                       │
│            /                        │
│           / Rocket                  │
│                                     │
└─────────────────────────────────────┘
```

# 12. `Game/Application` Layer

A small application layer will connect:

```text
Qt
 ↓
Simulation
 ↓
Controller
```

A `QTimer` will periodically advance the simulation.

For example:

```text
10 ms
 ↓
Simulator::step()
 ↓
SimulationWidget::update()
 ↓
Qt redraw
```

The initial target is approximately 100 simulation steps per second.

---

# 13. Collision Detection

The rocket and balloon are represented by simple geometric objects.

Version 0.1 uses a circular collision model.

If:

```text
distance(rocketPosition, balloonPosition)
    < collisionDistance
```

the balloon is considered intercepted.

The simulation then enters the successful terminal state.

---

# 14. Simulation Failure

The simulation fails if:

* the rocket leaves the world boundaries
* the maximum simulation time is reached

The simulation should expose its terminal state so that future reinforcement-learning code can determine whether an episode succeeded or failed.

---

# 15. Rendering

Rendering and physics are separate.

The simulation contains the actual state.

Qt only visualizes that state.

Therefore:

```text
Simulation
     │
     │ state
     ▼
SimulationWidget
     │
     ▼
    Qt
```

The simulator should remain usable without rendering.

This is important for future reinforcement-learning training, where thousands or millions of simulation steps may be executed without displaying every frame.

# 18. Explicitly Out of Scope for Version 0.1

The following are NOT part of Version 0.1:

* reinforcement learning
* neural networks
* computer vision
* simulated camera
* real camera
* MCU
* Raspberry Pi
* ESP32
* STM32
* realistic aerodynamics
* wind
* moving balloons
* 3D physics
* hardware control
* realistic propeller simulation

These will be considered only after Version 0.1 is working reliably.

# 19. Definition of Done

Version 0.1 is complete when:

1. The application starts successfully.
2. A rocket and balloon are rendered.
3. The simulation starts automatically.
4. The rocket autonomously determines how to steer toward the balloon.
5. The rocket moves according to the implemented physics.
6. The rocket can successfully intercept the balloon.
7. The simulation detects success.
8. The simulation can be reset.
9. The controller is separated from the simulator.
10. The simulator could theoretically be run without the Qt graphical interface.

The last requirement is particularly important because the simulator will eventually become the environment used for reinforcement learning.
